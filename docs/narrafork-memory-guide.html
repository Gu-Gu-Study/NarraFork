模型到底记住了什么？
NarraFork 的记忆链路

从一条用户消息出发，逐次拆开模型请求：哪些内容已保存，哪些正在本轮运行中，哪些真正被发送给 LLM。

代码基线：当前工作区 package.json 版本 0.9.1 · 以源码实现为准 · 示例 ID、摘要和文本为教学简化。

核心关系：数据库保存历史和状态 → 程序选择有效内容 → 组装提示词与工具定义 → 请求 LLM。页面上能看到的旧记录，可能已被摘要替代，或只用于展示。
01 / THE THREE STATES

先区分三种“记忆”状态

持久层 / DATABASE

可以恢复的记录

消息正文、会话引用、工具输入输出、当前摘要、Spec 文件版本、知识条目。默认保存到本机 SQLite；代码也支持配置 PostgreSQL。

结束一轮、刷新网页或重建运行时，不会因此清空这些记录。

运行层 / ACTIVE LOOP

本次执行的工作状态

history、当前输入、pendingToolResults、待注入消息、工具完成计数、已命中的知识集合。

同一次 loop 内追加；进入新的 pass 时，可从持久记录重新构建。

请求层 / PROVIDER PAYLOAD

模型实际读到的内容

有效系统提示词 + 有效历史 + 当前输入 / 工具结果 + 工具定义 + 模型参数。

不同 provider 会重新投影成各自协议。数据库 JSON 不会整体原样发送。

持久保存程序准备 / 内存历史发送给模型
用户消息 / 数据库先收件；认领后写 user 消息与 refs。读取当前摘要及有效历史。
→
组装当前上下文系统提示词 + 历史投影 + 当前输入 + 知识提示 + 工具定义。
→
provider.chat()发送一次 LLM 请求，接收文本、reasoning 或工具调用。
若模型调用工具：执行工具 → 保存结果、补充内存历史 → 收集提醒与通知 → 再发一次 LLM 请求。
若模型回答完毕：检查排队消息、后台通知、任务续跑 → 有工作则进入新 pass；没有则 idle，等待下一次输入。
三个时间尺度：“用户发一条消息”是一次输入；loop turn 是一次模型请求；orchestrator pass 是一次完整 agent loop 执行。一个用户输入可以产生多个 turn，也可能因续跑产生多个 pass。

02 / FROM USER TO IDLE

一次提问，直到本轮结束

接收与排队

前端请求 POST /api/narrators/:id/messages。主会话通过 runtime mailbox 收件。空闲时认领输入；忙碌时根据发送模式排队、切入或中断。收到 HTTP 请求不等于已经进入模型聊天历史。

物化用户消息

认领后通过 feedMessage 等路径写入 narrator_messages 的 user 行，并建立 narrator_message_refs。附件按引用保存，后续按 provider 需要读取。记录本轮触发用户，用于知识库 ACL。

新 pass 开始：准备历史

先处理应落库的待注入内容，读取当前 contextSummary 与最近成功 compact 后的有效消息。provider history builder 将最后的用户文本整理为当前输入，工具结果可单独作为待重放输入，避免当前用户消息发送两遍。

拼装第一次 LLM 请求

加载项目/全局指令，构造 system prompt；按当前 provider/model 格式化可用工具。实际输入文本存在时，进行被动知识匹配：命中、权限过滤、去重后将摘要提示持久化并加入本次输入。

流式响应：边输出，边保存

assistant 文本与 reasoning 可以在流期间形成 partial message 并追加 block；工具输入流尚未完整时主要维护运行快照。完整 tool-use block 到达后建立对应的持久工具记录。最终 assistant 事件保存或完成完整消息，并广播给页面。

如果调用工具：执行、记账、再次问模型

工具完成后保存 outputJson、状态、用时；loop 补齐 assistant 的 tool call 和待发送 tool result。工具输出可能命中知识条目；达到工具计数时生成任务/行为提醒，后台完成或团队消息也可在工具边界交付。它们进入同一用户任务中的下一次 LLM 请求。

回答结束后：判断继续还是 idle

模型没有后续工具工作时 loop 返回。orchestrator 检查排队输入、注入、压缩状态、Spec 自动续跑等。有继续条件则开始新 pass，从数据库重新准备；否则状态转为 idle。后续用户输入再次走此流程。

03 / REQUEST ANATOMY

每次给 LLM 的“提示词”是什么

提示词并不只是一个大字符串。通常是 system + 对话序列 + 当前输入/工具结果 + 工具定义。当使用 OpenAI Responses 时，一部分 system 内容会放到顶层 instructions。

有效 system prompt 的构建顺序

01叙述者自定义 prompt；为空时采用全局默认 prompt
02当前 contextSummary，标题为 ## Conversation Context（有摘要才追加）
03消息发送者解释规则；当前工作目录与 Shell 使用规则
04可用时的执行设备信息；Dynamic Spec 的使用说明
05项目指令：按 AGENTS.override.md → AGENTS.md → AGENT.md → CLAUDE.md 取第一个可读文件
06全局指令：从预设候选路径取第一个可读文件；文件引用格式规则
07适用时的回复语言要求和计划模式提醒

system 构建只注入 Spec 的使用说明，并不会自动把全部 Spec 文件正文塞进去。任务/行为正文由主动读取与消息注入路径提供。非首个 loop turn 的准备钩子会重建 prompt；压缩完成或模型切换也可能更新。

提供商协议system 放哪里工具调用 / 结果数据库 sys 注入行
Anthropic Messages顶层 systemassistant 的 tool_use；user 的 tool_result兼容路径映射为 user；当前支持中途 system 的官方路径可保留 system
OpenAI Chat Completionsmessages 中的 system 行assistant 的 tool_calls；role: tool 行投影为 user；不等同于 system prompt
OpenAI Responses提取为顶层 instructionsfunction_call 和 function_call_output 输入项投影为 user 输入项
两个“system”要分开：长期有效的 system prompt 是独立组装的指令；数据库中的 sys 是会话里的上下文消息。任务提醒、通知等通常沿消息路径送达，并非全部变成顶层 system。
哪些内容不会原样回放？
  • disp 行只显示在 UI，SQL 历史查询已排除。
  • 主会话不会把子代理整个消息树直接并入自身历史；子代理拥有独立的上下文加载路径。
  • 图片存储引用在准备请求时重新读取，转换为当前协议需要的图片 block 或 data URL。
  • reasoning/thinking 依 provider 与来源兼容性处理，不能保证跨模型原样回放；某些 block 会剥除或降级。

OpenAI Responses 路径显式使用 store:false 并发送本地组装的历史；不要将这个字段概括为全部 provider 的统一请求参数。

注入的四种调度意图

none

只保存行。没有立即请求模型的承诺，之后重建历史时可能读到。

onNextTurn

保存行，同时把文本交给正在运行的 loop 的下一次请求准备。避免当前内存快照漏掉新行。

interject / wakeIfIdle

前者请求工具边界切入；后者空闲时启动工作。它们表示调度动作，历史回放不会再次执行当年的唤醒意图。

避免重复：当前 pass 可以采用文本的内存交付，后续 pass 则重读持久消息；两条路径应分别作用于不同请求。若只写数据库，不交付当前 loop，下一次请求可能仍使用写行之前的内存历史。
知识库不等于自动记住所有聊天

被动注入只支持 summary / off，默认最多 3 条。依条目配置的关键词匹配，未配置关键词的条目仍可主动搜索。去重按叙述者与 compact 周期管理，发生 compact 后可重新注入。

主动 KnowledgeSearch 默认使用当前用户个人版本覆盖视图，KnowledgeRead 再做权限验证。被动摘要来自当前条目候选，不应假定也自动覆盖为个人草稿。本次相关链路没有发现聊天自动转成长期用户画像或 embedding 召回的实现。

07 / COMPACTION

压缩改变的是“模型读取边界”

假设原消息顺序是 U1 A1 U2 A2 U3 A3。手动设置 beforeMessageId=U3，表示压缩 U3 之前的对话，U3 本身不进入该次摘要。

压缩前

模型读取完整有效序列

U1A1U2A2U3A3

system = 基础指令
history = 上述有效消息

压缩成功后

早期消息由摘要承接

U1A1U2A2M / isCompact=1U3A3

system = 基础指令 + S(U1,A1,U2,A2)
history = U3 A3
划掉的消息仍在数据库中，只是不再按旧原文进入当前模型历史。

先建立 compacting marker

将 marker 插在 U3 前；尚未成功时不设置有效 compact 边界。记录进行中的尝试和状态，支持取消、失败与重试。

向摘要模型发额外请求

输入 = 上一次摘要（如有）+ 本次待压缩消息的文本表示 + 工具输入/输出摘要 + 同步问答结果 + 最新任务文本。指令要求保存目标、约束、发现、进展和相关文件。过长则按摘要模型窗口进行分块级联总结。

成功 finalize

同一事务更新 marker summary、ref 的 isCompact=1、会话 contextSummary。失败不切换成功边界，不应用失败摘要。共享 marker 会先复制到当前会话私有行。

在请求边界重建

运行中的 loop 重读新边界之后的历史，更新 system prompt，再发下一次 chat。不是直接修改一份已经发出的请求。数据库中的 marker 本身不作为普通对话回放，摘要通过 contextSummary 进入 system。

情况具体行为
自动触发模型窗口 ≤ 600,000 token：默认 95%；更大窗口：默认 75%。可配置，实际依 provider/context usage 与恢复路径决定。
“保留 2 pairs”默认配置为 2，但实现选择最后 keepPairs × 2 条 user/assistant 消息行。assistant 工具调用也可能占一行；不等于严格保留最后两次人类问答。溢出恢复还有其他边界路径。
编辑摘要更新 marker 与当前 contextSummary；共享消息先写时复制。后续请求使用修改后的摘要。
撤销压缩删除当前会话对应 marker ref，共享原记录在其他会话仍使用时保留；成功摘要字段被清空。只有一次 compact 时，原先被边界挡住的历史可重新进入准备过程。
局部分段压缩通过 segmentCompactId 隐藏指定片段 refs，模型查询过滤这些 refs；不同于全历史 compact 的 isCompact 起点机制。
持续信息要单独保存：Spec 任务和行为文件不依赖聊天原文是否仍在窗口内。compact 的摘要专用提示会读取最新 tasks；行为规则仍按自己的注入/读取路径恢复，不能保证都被摘要保留。

分叉复制的是上下文关系

父会话 N当前摘要 + 有效 refs + Spec 文件指针 + 会话配置
→
选择继承方式full / compressed / fresh；指定历史点时另有范围判断
→
新会话 N′独立新消息 refs；Spec 复制后独立；不沿用父上游会话 ID
模式聊天与摘要子会话首次模型请求
full复制指定点及之前当前窗口的 refs；正文共享。继承父 contextSummary。compact marker 之前的归档可惰性回填；不是把整份归档全部复制。基础指令 + 继承摘要 + 复制的有效历史 + 新输入
compressed额外调用摘要模型；当前摘要 + 最多 50 条模型历史行参与 fork summary。子会话保存新的 contextSummary 和 compact marker。基础指令 + 新摘要 + 子会话新输入。即使复制展示历史，它也会被新 marker 隔在模型起点之前。
fresh不复制聊天 refs，不生成 contextSummary；仍继承部分配置和父系统提示词。继承的基础指令与当前目录指令 + 新输入；不能理解成所有指令、Spec、知识都清空。

Spec 与聊天是两个独立轴

三种模式的 fork 都会另行异步复制 Spec namespace。子命名空间初始指向同一批文件版本，后续写入增加新版本并切换自己的指针，父会话不受影响。

默认 carryover 是展示一张任务继承卡，供用户查看、清任务或重置 Spec；卡是 disp，不会进入模型历史。特定调用方可选 clear 清空子任务，其他 Spec 不因此全部清空。

章节 fork 还会处理 Git 分支、worktree 和文件状态；会话 fork 的记忆继承只是其中一部分。“模型知道什么”和“分支上的代码是什么”需要分别判断。

历史点分叉：摘要时间范围不一定严格对齐
