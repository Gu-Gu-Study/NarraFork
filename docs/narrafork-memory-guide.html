NARRAFORK / MEMORY IN ONE PAGE

信息怎么存，模型怎么看？

NF 把信息保存下来，需要时取出，组装成一次请求发给模型。你看到的“记忆”，主要就是这条信息流。

下面只看一条主线：信息从哪来 → 什么时候存 → 模型收到什么。

01 / 先看全貌

每次回答前，NF 都要准备模型输入

信息来源用户说的话
工具读到的资料
任务、知识、指令
→
NF 保存消息与工具结果自动记录
任务与知识需明确写入
指令文件由用户维护
→
取出 · 组装请求选择有效历史和摘要
读取适用指令
加入本轮输入与工具结果
→
模型接收根据这次收到的内容
回答问题
或提出工具调用
回答会被保存；如果调用工具，执行结果也会被保存，并交给下一次模型请求。

什么时候存？
用户消息认领后；模型响应到达过程中；工具执行完成后。任务和知识在明确执行保存操作时存。

什么时候取？
新一轮执行时重建有效历史；同一轮工具循环中追加新结果。需要额外资料时，模型可调用工具读取。

存储里有的内容，不会全部自动发给模型。模型在某次请求里能读到什么，取决于 NF 为这次请求准备了什么。

02 / 一个连续例子

看看发给模型的请求，怎样一步步变化

例子里，你先告诉 NF：“演示机叫青松”，之后追问，再读取一份资料。

以下是依据实现简化的 Chat Completions 请求节选，不是生产抓包。省略模型参数、工具 schema 和身份标记；重复背景用短句表示。蓝边是发出的请求，黄边是模型返回。

1

你说一句话：先保存，再发给模型

你发送原话→NF 保存→原话进入请求
发给模型 · 第一次请求 这里的 user 就是你刚说的话 
{
  "messages": [
    {"role": "system", "content": "你是编程助手。请用中文回答。"},
    {"role": "user", "content": "演示机叫青松。"}
  ]
}

system 的来源基础提示词 + 项目／全局指令等。这里缩写成一句话。

模型回答“好的，演示机叫青松。”

保存时点：用户消息在被认领后保存；模型回答在响应到达过程中保存。两条都成为这个会话的记录。

2

你再问：NF 把之前的对话也带上

保存新问题→读取有效历史→旧对话 + 新问题
发给模型 · 第二次请求 重点看：旧原话又出现了 
{
  "messages": [
    {"role": "system", "content": "你是编程助手。请用中文回答。"},
    {"role": "user", "content": "演示机叫青松。"},
    {"role": "assistant", "content": "好的，演示机叫青松。"},
    {"role": "user", "content": "演示机叫什么？"}
  ]
}

模型回答“演示机叫青松。”

历史的来源NF 保存的当前会话记录。模型这次能答出来，是因为请求里有“青松”。

保存时点：新问题先保存；回答到达后继续保存。之后同样可以作为历史读取。

中间发生一次压缩：旧对话 → 摘要

NF 选出早期对话→单独请求摘要模型→成功后保存摘要

假设以上早期对话都被压缩，得到摘要：“演示机名为青松，用户已确认。”

成功后才切换：NF 保存摘要和新的读取边界。原消息仍在存储中，后续请求用摘要承接这些旧消息，不再自动逐条重发。

3

压缩后再问：名字来自摘要

读取已保存摘要→加入 system→模型据此回答
发给模型 · 压缩后的一次请求 本例假设没有其他近期消息 
{
  "messages": [
    {
      "role": "system",
      "content": "你是编程助手。请用中文回答。\n\n## Conversation Context\n\n演示机名为青松，用户已确认。"
    },
    {"role": "user", "content": "演示机叫什么？"}
  ]
}

摘要的来源额外摘要请求生成、NF 成功保存的当前会话摘要。实际请求还会带上压缩边界之后的近期历史。

模型回答“演示机叫青松。”

保存时点：摘要在压缩成功时保存；本轮问题和回答照常保存。摘要可能遗漏细节，不能当作原文的完整备份。

4

需要额外资料：读到了，下一次请求才用上

接着你问：“读一下演示机的访问地址。”NF 先保存问题并发给模型；模型决定调用 Read。

模型提出 Read→NF 执行并保存结果→下一次请求带上结果
模型返回 · 工具调用 这是模型的响应，还没读到文件 
{
  "role": "assistant",
  "tool_calls": [{
    "id": "read_1",
    "type": "function",
    "function": {
      "name": "Read",
      "arguments": "{\"file_path\":\"demo.txt\"}"
    }
  }]
}

NF 执行读取 demo.txt，得到：“演示机访问地址：http://192.168.1.8:7779”。

发给模型 · 工具执行后的下一次请求 同一个用户任务，发生了下一次模型请求 
{
  "messages": [
    {"role": "system", "content": "基础指令 + 当前会话摘要（同上，省略重复正文）"},
    {"role": "user", "content": "读一下演示机的访问地址。"},
    {
      "role": "assistant",
      "tool_calls": [{
        "id": "read_1",
        "type": "function",
        "function": {
          "name": "Read",
          "arguments": "{\"file_path\":\"demo.txt\"}"
        }
      }]
    },
    {
      "role": "tool",
      "tool_call_id": "read_1",
      "content": "演示机访问地址：http://192.168.1.8:7779"
    }
  ]
}

这里只节选本次工具往返，之前压缩后保留的近期消息省略。实际请求会保留有效近期历史；此例也省略了 tools 定义。

模型最终回答“文件中的访问地址是 http://192.168.1.8:7779。”

保存时点：完整工具调用到达后建立记录；工具完成后保存结果；最终回答到达后继续保存。地址是在本次 Read 的结果里进入模型请求的。

03 / 提示词从哪来

一次请求，主要看这三部分

system

基础提示词
+ 当前目录的项目指令
+ 全局指令等规则
+ 当前会话摘要（有才加）

messages

有效聊天历史
+ 当前用户输入
+ 工具调用与结果
+ 已交付的上下文提醒

tools

本次可用工具的名称、用途和参数说明。
这是“怎么调用”的说明，不是工具读到的资料。

上面按用途解释。Chat Completions 协议中 system 也是 messages 数组中的一项；NF 会把来源不同的内容组装为对应消息。

任务笔记 Spec 从哪进来？

AI Write / 用户面板保存→保存当前会话任务→Read 或任务提醒→进入模型请求

例如保存“核对端口：待办”，后续 Read 返回正文，或按规则生成任务提醒。保存 Spec 不会让全部正文自动进入 system；system 主要先提供 Spec 使用说明。

知识库从哪进来？

明确整理并保存知识→关键词提示 / Search→KnowledgeRead 取正文→进入模型请求

关键词命中通常先给短摘录和条目 ID；模型需要正文时再读取。知识可以跨会话使用，取决于发布状态、项目与权限。聊天结束不会自动变成共享知识。

04 / 记住这三点就够了

判断“模型知不知道”，看这次请求

  1. 已保存，不等于已读到。信息要被取出并放入本次请求，才在这次请求中提供给模型。
  2. 压缩之后，通常是“摘要 + 近期历史”。摘要没保留的细节，需要再查来源；重新读文件得到的是当前文件内容。
  3. 独立新会话不会自动拥有旧聊天。Spec 按会话隔离，fork 可另行继承；知识按发布状态、项目和权限取用。
